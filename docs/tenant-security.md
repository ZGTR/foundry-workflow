# Tenant identity and isolation plan

Each tenant's workload credentials authorize only its own resources and permitted operations. Tenant identity follows every job through intake, storage, recovery, dispatch, callbacks and artifact access. Independently trusted tenants may share the deployment after the release gate passes.

## Tenant calls Foundry

Use OAuth 2.0 client credentials and issue short-lived access tokens for the Foundry audience. Register one workload identity per tenant, application and environment. Use a server-managed binding of trusted issuer and client ID to tenant, producer and allowed scopes. Validate signature, pinned issuer and JWKS, audience, access-token type or approved provider discriminator, time claims, client ID, and subject. Strictly validate claim types and intersect granted token scopes with the registration. Treat supplied tenant and producer fields as consistency checks. Use a distinct configured access-token issuer, separate from the service's outbound event producer name. Enforce registration deactivation with a bounded revocation delay and reject deactivated clients before any receipt lookup. Avoid logging credentials. [OAuth security BCP](https://www.rfc-editor.org/rfc/rfc9700.html), [JWT access token profile](https://www.rfc-editor.org/rfc/rfc9068.html)

Require mTLS and access-token authorization at the tenant production ingress. The tenant verifies Foundry's hostname and certificate, and Foundry's gateway verifies the tenant's certificate and revocation status. Prefer certificate-bound OAuth tokens and verify the presented peer certificate against the token's cnf.x5t#S256 thumbprint. If the approved issuer lacks that profile, require the gateway to verify both credentials on each call against the same registered workload and tenant. Test the selected issuer profile in staging. If TLS terminates at a gateway, restrict access to the authenticated private proxy path, use TLS on the backend hop and accept a single certificate identity derived from the verified connection. Strip client-supplied identity headers at the edge and exercise spoofing and revocation checks before release. [OAuth mTLS and bound tokens](https://www.rfc-editor.org/rfc/rfc8705.html), [AWS ALB mTLS](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/mutual-authentication.html)

Prefer mTLS or private_key_jwt for client authentication at the issuer where supported. Cognito documents a client ID and secret flow with custom scopes. Confirm issuer support for Foundry audience and proof-of-possession requirements. If using the documented secret flow, protect and rotate a unique secret per workload and enforce same-client certificate binding on every request. An X-API-Key is optional for metering and confers no authorization. A long-lived key cannot supply short-lived, audience-scoped access or cryptographic proof of possession by itself. [OAuth security BCP](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.5), [Cognito M2M and resource servers](https://docs.aws.amazon.com/cognito/latest/developerguide/cognito-user-pools-define-resource-servers.html)

| Tenant operation | Proposed authority |
| --- | --- |
| Submit a v2 trigger | workflow:submit and an enabled tenant-to-trigger and workflow grant |
| Read progress or history | workflow:read and ownership of the job |
| Submit a v2 stage result | workflow:complete, configured executor identity, matching tenant, workflow, stage and active attempt fence |
| Subscribe to events or receive callbacks | Operator-provisioned tenant-specific destination, event types and delivery identity |
| Manage tenants, grants, weights, quotas or manual leases | Separate internal operator or service identity and audit trail |

Check scopes at each application entry point. The tenant-facing application profile uses an allowlist of v2 submit/result and owned state/history routes. Other routes, including v1 writes, raw lease commands, OpenAPI and debug paths, are absent from this profile; enforce the same allowlist at the gateway. Enable this profile only on the ECS deployment with a private application origin and verified mTLS edge. The legacy Lambda/API Gateway wildcard route is internal only and must not expose the shared ledger or bypass the tenant gateway. Internal routes use a separately authenticated principal class with explicit service/operator grants. Legacy trusted callers use their existing internal profile and cannot write scheduler-owned jobs.

Register immutable, lowercase ASCII opaque tenant IDs with a canonical grammar and length. Reject noncanonical input without trimming, case-folding or Unicode normalization. Use byte-exact ownership, uniqueness and join comparisons on SQLite and MySQL (binary storage/collation plus canonical application validation). Audit existing identifiers and case, accent and padding collisions before cutover. Fail the migration on unsafe or unmapped rows. Never silently coalesce or reassign legacy identities.

Operator grants identify the tenant, producer, event type and exact immutable workflow definition digest. An event requests the newest granted immutable definition per matching workflow key. Silently omit globally matching keys for which the tenant has no grant. If no definition is authorized, return a generic denial. Authorize the whole selected fan-out before any job persists. Register and audit new digests before catalog rollover. Existing running jobs continue on their pinned definition with currently authorized executors. Return an identical deduplicated receipt only after checking that the active workload still has the grants for every bound definition; conflicting receipt content stays a conflict without revealing details. Keep platform administration, raw ledger commands, debug endpoints and fleet views on the internal perimeter. Keep health responses coarse. Use indistinguishable missing-resource and foreign-resource responses. Enforce ownership in queries and mutations including child rows, deduplication, outbox reads and cache keys. Tenant credentials never authorize database, shared bus, metrics or backup access. [OWASP API1 Broken Object Level Authorization](https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization/)

## Foundry calls the tenant

Start with authenticated HTTPS submission and polling. For push, bind each callback destination to one tenant and expected server identity. The receiver validates a separate Foundry workload credential scoped to that destination. Foundry verifies the receiver's certificate and hostname. Prefer mTLS and a destination-audience OAuth token where the receiver supports that profile. For receivers that support signed webhooks, use RFC 9421 over TLS with tenant-specific key registration. Cover the method, target, content digest and event ID. Enforce signature freshness and replay protection. Keep the outbox event ID stable across retries and sign each attempt. [RFC 9421](https://www.rfc-editor.org/rfc/rfc9421.html)

Verify endpoint ownership at registration and audit changes. Use egress policy to limit destinations. For public callbacks, reject private, local and metadata addresses, validate resolved endpoints at connection time and disallow redirects. Store keys and credentials in managed secrets with overlapping rotation windows. Route dispatches, terminal events, dead letters and replays only to the authorized owner. Carry the trusted outbox row owner through delivery. Verify it matches the envelope, job binding when applicable, and allowlisted destination tenant before publishing. Keep the service-managed EventBridge bus private. For destination deliveries, persist one owner-bound delivery record per outbox event and authorized destination version. Use a short transaction to claim delivery with a lease and fence, send after commit, and acknowledge with owner and fence checks. Quarantine malformed events or unavailable and revoked destination registrations, with bounded retry/backoff for transient failures and independent progress for later rows. Replay only with the original owner and current authorized routing. A replay never changes a tenant binding. Resolve artifact references against registered tenant storage and use least-privilege policies and short-lived access. Keep payloads and artifact capability URLs out of logs.

## EventBridge and SQS

The documented shared-bus contract assumes publishers are trusted for its allowed tenant set. Use a private service-managed common bus and HTTPS submission/results for initial external tenants. Disable the legacy shared consumer in the tenant-facing deployment, and remove all enrolled tenants from the allowed identities of any older consumer sharing the ledger before onboarding. Keep recovery, scheduled admission and outbox draining independent of the presence of an ingress consumer. Validate that a shared bus event cannot resolve to a registered HTTPS tenant. The private service bus accepts only service-controlled roles. Its routing configuration is part of enrollment. Before enabling direct tenant pub/sub, provision tenant-specific IAM publisher identities and ingress channels. Bind tenant and producer to trusted channel provenance enforced by IAM and queue policies. Validate claimed identity against this binding before minting a principal. Use infrastructure-controlled routing and tenant-specific permissions for visible event targets, with the same scopes and replay rules as HTTPS. [EventBridge bus permissions](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-event-bus-perms.html)

## Release gate

Run with two separately provisioned tenants plus separate submitter, executor, callback and operator identities. Use SQLite and staging MySQL for persistence and deployed gateway and AWS policies for transport.

- Verify valid operations succeed. Wrong issuer, audience, token type or expiry, inactive client, missing scope, invalid or mismatched certificate and untrusted proxy context all fail. Prove rotation and revocation.
- Try foreign job and stage IDs, competing tenant or producer claims, unauthorized operation scopes, and foreign or stale result correlations. Compare foreign and missing responses and verify zero cross-tenant state changes or outputs. Check that tenant clients cannot reach internal routes.
- On MySQL exercise case, accent and trailing-space aliases and the byte-exact ownership migration. Exercise identical identifiers across tenants, duplicate events, stale leases, transport misrouting, DLQ redrive, operator replays, migrations and mixed versions. Verify that each tenant receives only its own events and artifacts.
- Verify callback receiver identity and Foundry identity, stale and replayed signatures, duplicate deliveries, unauthorized destinations and cross-tenant redelivery. Audit logs, metrics, backup and restore access.
- Run one tenant at quota while another submits and finishes jobs. Review and record isolation evidence before onboarding independently trusted tenants.
